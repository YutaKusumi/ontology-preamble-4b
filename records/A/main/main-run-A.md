## 1. 不利な材料（先に）

1. **橋 4B の一回目の起動が、Hugging Face の 429 で止まった。** 校正腕のサーバを立てる前の重みの版の照会が `429 Too Many Requests` を返し、起動器は `SystemExit: 1` で止まった（その下に出た `TypeError`・`AttributeError` は IPython の traceback 整形器が落ちたもので、原因ではない）。**試行は一件も走っていなかった**（セッション記録は記帳だけで、校正腕の走行ディレクトリは無かった）。コーディネータは、**同じランタイムで同じセッション番号（1）のまま**数分おいて走らせ直し、完走した。根拠は正本 `sessions.number_rule`（番号はランタイムを新しく起こすたびに進める）と、起動器の再開の設計（既存のセッション記録を読んで続ける）。校正腕の `incomplete_rule` は校正腕が走って件数が足りない場合の規則で、今回は当たらないと読んだ。**この読みはコーディネータの解釈で、登録者が承認した**（逐語「判断 2については、ご提案の内容を承認します。」）。セッション記録の log には一回目の段（repo・gpu・pip）が残り、二回目の段が続く。
2. **橋 8B のセッションだけ、pip freeze の SHA16 が違う**（104046D3EDBBD2DC・ほかの 8 セッションはパイロットと同じ C64B7D0E40293DAE）。主な版（vLLM・torch・transformers・tokenizers・huggingface_hub）は同じ（§2）。回収の器は pip freeze を照合の項目に持っておらず、**回収の後に表を組んで初めて気づいた**。ランタイムを削除する前に、そのランタイムの `pip freeze` の全文を保存した（`records/A/main/pip-freeze-bridge-8B-s1-2026-09-17.txt`・16,132 バイト・789 行・SHA16 は記帳の値と一致）。**ほかのセッションの全文は残っていない**（起動器は SHA16 だけを記帳する）ので、**どの包みが違うかは特定できない**。正本 `environment_rule.record` は pip freeze の SHA を記帳の項目としており、セッション間の同一を求める規則は無い（規則違反ではない）。ただし橋の 8B の L4 側では、**環境（L4 と A100）・同時要求数（12 と 24）・時点・pip freeze の差が重なっており、分離できない**（正本 `environment_rule.concurrency_disclosure` の交絡に、pip freeze の差が加わる）。
3. **表示の異常を「カーネルが落ちた可能性が高い」と誤って報告した。** 橋 8B の走行中（2026-09-17 11:39 ごろ・日本時間）、Colab の画面が「接続中」「実行を再開中」のまま戻らなくなった。ブラウザのコンソールの記録では、カーネルとの websocket が code 1006 で閉じ、「ランタイムの異常終了時刻」の警告が出て、**3 秒後に同じカーネルへ再接続していた**。コーディネータはこれを見て登録者に「カーネルが落ちて再起動された可能性が高い」と伝えたが、**ターミナルで確かめると誤りだった**（カーネルの親プロセスの経過時間は再起動を示さず、vLLM のサーバと走行器も生きており、行数は増え続けていた）。直後に訂正した。表示は後で回復し、走行は完走した（§2 の先取り・redo・終了コードはすべて零）。
