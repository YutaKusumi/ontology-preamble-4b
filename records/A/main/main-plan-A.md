## 5. 走行中の保存と再開（登録者の指示・2026-09-16）

- 指示（逐語）: 「ColabとAPIでの本試行共通なのですが、途中で、意図せずランタイムが解除される事態も想定して、随時、Google Driveにデータが保存されるように注意をお願いします。」
- **確かめた事実**（`records/A/api-rerun-cost-A.md` §6）: 走行器は各試行の処理が終わるたびにロックを取り、raw と trials を一行追記して閉じる。Colab では `results/` が Drive の実体への symlink なので、**書いた分はその時点で Drive に載る**。起動器は走行キーごとにセッション記録も Drive に保存し直す。したがって切断で失うのは「その瞬間に生成中だった試行」だけ。
- **運用の注意**: (i) 切断に気づいたら、**新しいランタイムで次のセッション番号**として同じ一行を走らせる（走行器は既存の行の trial_id で続きから再開し、行数と n_ok が目標に達した走行キーは飛ばす）。(ii) zip を待たずに、時々 Drive の `op4b-stageA/results/` の中身が育っていることを確かめる。(iii) 一つの走行キーが複数のセッションにまたがったら、**両方のセッションに属するものとして記帳する**（正本 `sessions.resume_rule`・校正腕の注はどちらの異常でも付す）。
- 各セッションの終わりに起動器が zip を Drive に書く。回収は常設の許可（D-35）でコーディネータが落とし、**zip の SHA-256（ランタイム側と手元）と、中のファイルの SHA16（セッション記録の `files_sha16_lf`）を突合**してから `results/` に置く（パイロットと同じ運び・器は一時置き場の `collect_pilot_A.py`）。

## 9. 止める規則（運用・凍結物を変えない）

1. 校正腕が帯を外れたら、機種の走行に進まずに止める（§4）。
2. GPU の割当が正本の環境と違えば走らせない（例: 8B に L4）。**32B に 80GB が取れなかったときは三段で運ぶ**（登録者裁定 2026-09-16）: (i) ランタイムを取って 80GB なら 32B を走らせる。(ii) **40GB だったら、そのランタイムでは 8B か 14B を走らせる**（どちらも `if_40GB` の登録どおり・同時要求も 80GB のときと同じ値）。32B はそのまま待たせ、別の機会に 80GB を狙う。(iii) 80GB が何度も取れない場合にだけ、時間貸し（環境値「第三」）を登録者が**見積もりと上限額を先に記帳して**決める。——この運びなら割当の運に左右されても待ち時間が無駄にならず、32B だけが後ろにずれる。データ取得への不具合は無い（セッション番号は相と機種ごとに数えるので走行キーも seed も変わらず、記録される環境値は 40GB でも 80GB でも A100・メモリ級は別の欄に残る）。ただし (a) セッションが一つ増えるぶん校正腕が 400 試行増える、(b) 32B の走行だけ時点がずれる（設計は時点を統制しておらず、走行間の変動は錨反復で見る）、(c) 同時要求の詰め合わせで生成が厳密に同一にならない可能性がある（分けても分けなくても生じる・測っていない）。
3. 起動器が止まったら、止まった箇所と記帳を記録して登録者に諮る。凍結物を直す必要があれば逸脱として承認を得る（逸脱台帳 D-37〜）。
4. 実測のユニットが見込み 76.98 の 1.25 倍（96.2）を超えたら、残りの走行の前に登録者に諮る（費用の停止規則 324.7 とは別の、早めの警戒線として置く）。
5. API 再走行の費用には機械の停止を置かない（§7）。
