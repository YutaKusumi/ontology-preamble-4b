# 同一性選別の判定の四条（裁定 D150 候補）に関する検分票（系統外・Gemini）

- **検分者**: Gemini（系統外・Google）
- **対象**: 段階 B 同一性選別の判定の四条（正本 `design/contrasts-B.json` SHA16 `5D45DFF3802F4D58`・判定器 `tools/identity_screen_B.py` SHA16 `8D9F4FB83139C426`）および関連資料
- **確認の範囲**: **束の外（公開リポジトリ等）は開いておらず、提供された資料の束（part1 〜 part4）のみから照合・検証した。**

## 1. 伺いたい四条に対する意見

### (a) 主判定の対: 【是認】
- **判定**: **是認**
- **理由**:
  同一性選別（門0.5）の本質は、「手元の実行環境が、プログラム全体の基準点（アンカー）である API 既測（stageVp/stage1）と同一個体・同一重みとみなせるか」を確認することにあります。段階 A においても「手元の vLLM スタック 対 API 既測」が主判定であったため、段階 B において「手元の transformers スタック 対 API 既測」を主判定に据えることは、プログラムの通底する型と完全に一致しています。
  別案の「vLLM 対 transformers」を主判定にした場合、両者が揃って API 既測から乖離していた場合に見落とすリスクが生じます。また、正本 `stacks` が要求する三者間比較についても、API↔vLLM および vLLM↔transformers の距離が同一テーブルに記述統計として完全開示（`identity_screen_B.py` 246〜251行目）されるため、判定の客観性・透明性は十分に担保されています。

### (b) vLLM の件数の出所: 【是認】
- **判定**: **是認**
- **理由**:
  段階 A の門0.5 の記録（`records/A/identity-screen-A.json` の `local_counts`）は、同一機種・同一環境下で走らせた凍結データであり、`identity_screen_B.py` 211〜219行目において段階 A の凍結記録（`records/freeze-A-2026-09-16.json`）の SHA16 と厳密に突合（`check_pin`）した上で読み込まれています。
  段階 B のために追加で 2,080 試行の vLLM 走行を重複実行することは費用の浪費であり、合理的ではありません。また、別案の「二スタックのみにする」案を採ると、正本 `stacks` の登録（三スタック比較）と乖離し、段階 A から段階 B への推論エンジン移行（vLLM $\rightarrow$ transformers）に伴う差異の記録が失われてしまいます。凍結記録による釘打ちを前提とした再利用は極めて堅牢です。

### (c) 補助の検定: 【是認】
- **判定**: **是認**
- **理由**:
  段階 A においても補助検定（Freeman–Halton MC + Fisher 統合）は `affects_verdict: false` であり、合否判定には一切影響しない参考値でした。段階 B の正本には `aux` の登録が存在しないため、凍結直前に正本外の統計量を器の側で勝手に捏造しないという判断（「登録の無い統計を作らない」）は、事前登録の厳格な規律として完全に正当です。主判定（平均差 5 pt 以内、最大差 12 pt 以内）のみで門0.5 としての識別機能は完結しています。

### (d) 排他の件数の出所: 【是認】
- **判定**: **是認**
- **理由**:
  排他の優先順位（書式外 $\rightarrow$ refuse $\rightarrow$ 破局 $\rightarrow$ その他）は段階 A で確定した規約であり、これを段階 B で再実装すると、些細なコードの差異による判定ズレのリスクを抱え込みます。「採点・分類経路は凍結した関数を直接呼ぶ（再実装しない）」というプロジェクトの大原則に忠実であり、`identity_screen_B.py` の自己検査（163〜170行目）において、段階 A の実績値（平均 1.062 pt・最大 8.125 pt）がビット単位で完全再現されることが実証されています。再現性と安全性において最善の選択です。

## 2. (e) 四条のほかの見落としの指摘

器のソースコード（`tools/identity_screen_B.py`）および正本・草案を精査した結果、**1件の実務的・運用上の重大な矛盾（型の穴）**を発見しました。

### 【重大】不合格時における終了コード `sys.exit(2)` と `fail_reading` 規約の衝突
- **(a) 置き場**:
  - `tools/identity_screen_B.py` 283行目
  - 正本 `design/contrasts-B.json`（`identity_screen.fail_reading`）
  - 草案13B §2.1（part4）
- **(b) 事実**:
  - `tools/identity_screen_B.py` の末尾（283行目）は以下のように実装されています：
    ```python
    sys.exit(0 if verdict == 'pass' else 2)
    ```
  - 一方で、正本 `identity_screen.fail_reading` および草案 §2.1 には以下のように明記されています：
    > 「不合格でも B は別個体の内側で完結する測定として実施できる（A の錨の点を規模の線に転記しないことは A の凍結どおり）」
- **(c) なぜ問題か**:
  - 門1（`gate_B.py`）は「操作不能」の撤退条件であるため、不合格時に `sys.exit(2)` でプロセスを停止させるのが正当です。
  - しかし、同一性選別（門0.5）は、**たとえ不合格（fail）であっても段階 B の実験自体は中止せず、「別個体の内側で完結する測定」として後続（方向抽出 $\rightarrow$ 調整走行 $\rightarrow$ 本走行）へ進むことが事前登録された正式な規約**です。
  - それにもかかわらず、`identity_screen_B.py` が不合格時に終了コード `2`（エラー終了）を返してしまうと、Colab やシェルスクリプトで一括実行パイプライン（`run_all` 等）を組んでいた場合、プロセス全体が異常終了として中断され、**正本が認めている「不合格時の継続測定」が物理的にブロックされてしまいます**。
  - 段階 A の凍結器 `tools/identity_screen_A.py`（part3）を確認すると、合否に関わらず正常終了（終了コード 0）で終わっており、合否は JSON/MD への記帳に委ねられていました。
- **(d) 直し方の案**:
  - **案1（推奨・段階 A 整合）**: 段階 A の器と同様に、合否判定にかかわらずファイル出力後は常に `sys.exit(0)` で正常終了させる（合否結果は `verdict: "fail"` として記録され、読み条項に従って解釈される）。
  - **案2**: 非ゼロ終了を維持したい場合は、パイプライン側で停止させないための引数（例: `--allow-fail-continue`）を設けるか、正本の運用手順に「選別不合格時でも終了コード 2 を無視して後続へ進む」旨の例外規定を明記する。
