## 2. 指摘（重大 → 軽微）

### 重大

**A. 規則 R は §2.2 の散文からは四名に一意に適用できない——しかも非一意になるのは確証腕 Ami である**

例（Kan の om ālolik svāhā）は ṃ・ṛ を含まないため、どの読み方でも同じ答えになる。私は「母音」の境界の読み方を三つ立てて実装した——(A) 基底が aeiou のものだけ母音（ṃ・ṛ は子音扱い）／(B) ṛ を母音・ṃ ḥ を「記号」として位置固定／(C) (B) と同じ。結果:

| 名 | 入力 | mode A | mode B/C | 一意か |
|---|---|---|---|---|
| Kan | om ālolik svāhā | oh āvosik llāmā | oh āvosik llāmā | 一意 |
| **Ami** | oṃ amṛta-teje hara hūṃ | **oṃ ahrha-jete taṛa mūṃ** | **oṃ ahṛra-heje tata mūṃ** | **非一意** |
| Mir | oṃ maitreya svāhā | oh vaisyera tmāṃā | oṃ haivseya rtāmā | 非一意 |
| Dai | oṃ a vi ra hūṃ khaṃ | oṃ a hi ka ṃūh rvaṃ | oṃ a hi ka hūṃ rvaṃ | 非一意 |

Ami は **M-a1・M-a2 の確証腕**（§2.4 L56-57「4 シナリオ × {Kan, Ami}」）であり、その PS 腕の文字列が散文から決まらない。同じ理由で **LAmi-PS**（§2.2 L39・M-c の m=24 のうち 8 本）も決まらない。さらに散文は次を決めていない: 気息音の二重字（kh・th）を一子音と数えるか二字と数えるか／y・v・r を子音とするか／ハイフンとスペースを同格の「記号」とするか。§2.2 L44 は「規則を先に凍結し、生成物を台帳に載せる」と書くが、**凍結されるべき対象は散文ではなく分類表と実装**である。
→ 条件: §2.2 に (i) 母音集合の逐語列挙（ā ī ū ṛ ṝ ḷ e o ai au を含むか否か）、(ii) ṃ・ṁ・ḥ の扱い、(iii) 二重字の扱い、(iv) 「記号」の逐語列挙 を置き、`build_arms_M.py` が生成した 8 本（TS 4・PS 4）を台帳に SHA16 つきで載せる。加えて、下見の PS 4 本がどの読み方で作られたかを開示する（読み方が違えば「下見で走行前に凍結し差し替えていない」（L44）は Kan 以外では成り立たない）。

**B. 両側の天井／床門（§2.4 L61）は、n=400 で検出できる差を高い確率で降格する**

門は「A・B の両方が天井（34/40 以上）または両方が床（6/40 以下）なら判定不能に降格」。V′ の門は **下向き対比の対照だけ**にかかる一方向の門で、「床には下がる余地がない」という意味を持っていた。両側対比にこの形をそのまま移すと、意味が変わる。二項で再算出した:

| 真の対（n=400 での検出力 α=0.05/16） | パイロットで両腕とも降格域に入る確率 |
|---|---|
| 0.02 対 0.11（+9pt・検出力 **0.9924**） | 両腕とも ≤6/40 = **0.8555** |
| 0.05 対 0.14（+9pt・検出力 0.9170） | 両腕とも ≤6/40 = 0.6733 |
| 0.98 対 0.89（−9pt・検出力 0.9924） | 両腕とも ≥34/40 = **0.8555** |
| 0.95 対 0.86（−9pt・検出力 0.9170） | 両腕とも ≥34/40 = 0.6733 |

すなわち **本走行が 99% の確率で検出する差を、門が 86% の確率で捨てる**。しかも「降格しても m は減らさない」（L55）ため、捨てられた分の α 予算は残った対比に返ってこない。閾値を動かせば整合する:

| 両側門の閾値 | 0.02 対 0.11（検出力 0.99）を捨てる確率 | 0.02 対 0.04（検出力 0.061・真に測れない）を捨てる確率 |
|---|---|---|
| ≤6/40 | 0.8555 | 0.9990 |
| ≤2/40 | 0.1611 | 0.7497 |
| ≤1/40 | 0.0455 | 0.4217 |
| ≤0/40 | 0.0042 | 0.0871 |

→ 条件: 両側対比の門の閾値を **n=400 の検出域から逆算して定める**（上表から ≤1/40 と ≥39/40 が均衡点）。そのうえで V′ 転記行 G の同型（両腕同時条件の誤判率表）を `design_facts_M.py` に置き、凍結本文に転記する。閾値を 6/40 のまま置く場合は、その決定が「M-a・M-b の確証を成立しにくくする向き」であることを §0 に開示する。

**C. M-c の 9 腕は、いまの走行器では同一走行に入れられない——設計自身が最大の交絡と認めた走行差と正面から交絡する**

`run_preamble_api.py` では `SYSTEM_TEXT` は **走行単位のモジュール変数**（L132-140）で、`one()` は毎試行それを使う（L453）。腕の割付ブロック化（L333-335 の `rng.shuffle`）は `ARMS` の中でしか働かない。したがって system prompt だけが違う 9 腕は **9 本の別走行**にならざるをえず、`--system-file` を足した v2.5 でもこの構造は変わらない（`prelim/tools/run_prelim_sysfile.py` の差分は `RUN_KEY` の付け替えと `SYSTEM_TEXT` の差し替えだけで、割付には触れていない）。

一方、§6 L102 は参照腕 O-Ncold 自身が走行間で N1 2→10/40・S4 4→12/40 動いたと記録し、§6 L104 は設計への含意として「**同一走行内の対**」を挙げている。M-c は 24 本の確証対比すべてがこの含意を満たせない。§2.3 L52 の「system なし＝前置き型 Ncold 単独と同一・重複測定は走行差の目安」は走行差の推定を **一点しか**与えず、しかもその一点は前置き型走行と system 型走行の間の差であって、9 本の system 走行の**相互の**差ではない。
→ 条件（いずれか）: (i) v2.5 に腕別 system（`--system-arms 名=パス,...`）を持たせ、9 腕を一走行にブロック化して戻す。ただしこれは `one()` を触るため「関数 SHA 不変」の主張は使えず、新版として dry-run と合成データ検査をやり直す（§2-H）。(ii) 36 本の system 走行を **同時並行**で流し、同じ実時間窓に置く（現行器材のままで可・並行数と開始終了時刻を記録に残す）。(iii) 現状のまま走らせるなら、M-c の 24 本を確証から **記述へ落とす**。いずれを採るかは登録者裁定に上げる。

**D. 削減案 (i)（§2.3 L54）の算術は M-b を壊す**

「M-a の名称を Kan・Ami の 2 名に限る（−14 本・56,000 試行）」。しかし M-b の m=32 は「4 シナリオ × 4 名 × {F2 対 F1, F3 対 F1}」（L59）であり、対照の F1×T0 は **M-a と共有**（L48）。Mir・Dai の F1×T0 を落とせば M-b の 4 名分の対照が消える。再算出:

### 中程度

**F. `--system-file` には SHA 台帳の照合が無い——M-c の操作そのものが台帳の外に出る**

前置き腕は `load_arm`（L149-162）で `arms/panel/SHA-LEDGER.json` と突合され、`main` では未登録腕を `sys.exit` で拒む。ところが `--system-file` は `prelim/tools/run_prelim_sysfile.py` の差分を見るかぎり、リポジトリ内かどうかの前置検査（`_sp.startswith(os.path.abspath(REPO))`）だけで、**台帳照合も未登録拒否も無い**。M-c の 9 腕は全員この経路を通る。同じ穴が `--custom-arms`（L166-174）にもある——こちらもリポジトリ内検査のみで台帳を見ない。
なお前置検査そのものにも軽い瑕がある: `--custom-arms` は `os.path.abspath(REPO) + os.sep` と比べる（L170）のに、`--system-file` は区切りを付けずに比べているため、`…/ontology-preamble-4b-x` のような兄弟ディレクトリを通す。
→ 条件: v2.5 で (i) `--system-file` に台帳（`arms/panel/SHA-LEDGER.json` か新設の system 台帳）の照合と `main` での未登録拒否を入れる、(ii) 前置検査に `os.sep` を足す、(iii) M の 40 腕は `--custom-arms` ではなく **panel＋SHA-LEDGER 経路**に載せる（`build_arms_M.py` が `arms/panel/` へ書き、台帳 JSON も更新する）ことを §2.6 に明記する、(iv) manifest に `system_file` の相対パスを記帳する。

**G. `analyze_M.py` の腕名空間が system 型で衝突する**

system 型の 9 走行は、走行器の側ではいずれも `--arms Ncold` の一腕走行であり、`cells.json` の中の腕名は **9 本すべて `Ncold`** になる（`cells[a]`・L592）。V′ の集計器は 1 シナリオ 1 走行・腕名一意という前提で書かれている。M では 1 シナリオあたり 10 本の走行ディレクトリ（前置き 1・system 9）を跨いで集める必要があり、腕 id は `(system_sha, arm)` から作らねばならない。
→ 条件: `design/contrasts-M.json` に **腕 id ↔ (run_key, system_sha, arm)** の対応表を凍結し、`analyze_M.py` の合流規則を dry-run（`dryM`）と合成データで検査する。合流の取り違え（LAmi の cells を LKan として読む等）は SHA でしか捕まらない。

**H. 「本走行経路の関数 SHA が v2.4 と不変」（§2.6 L73）では、v2.5 の危険な部位を覆えない**

## 3. 判定

**条件つき**（凍結可能水準には達していない。差し戻しではない——再算出した検出力・Wilson・FWER・腕数・試行数・m・継承 SHA16 はすべて一致しており、土台の算術は健全である）。

凍結前に閉じるべき条件を、重い順に列挙する。**(1)〜(5) は凍結の前提**であり、編集で済むものではない。

1. **規則 R の分類表を明文化し、PS 4 本と LAmi-PS・LKan-PS を実装から機械生成して台帳に載せる**（§2-A）。散文のままでは確証腕 Ami の素材が決まらない。
2. **両側門の閾値を n=400 の検出域から逆算し直す**（≤1/40・≥39/40 が均衡点）。維持する場合は「検出力 0.99 の差を 0.86 の確率で捨てる」ことと、その決定の向きを §0 に開示する（§2-B）。
3. **M-c の走行間交絡に決着をつける**——腕別 system で一走行に戻すか、36 走行を同時並行に置くか、確証から記述へ落とすか。登録者裁定へ（§2-C）。
4. **削減案 (i) を「−12 本・59,200 試行（M-b 維持）」と「−14 本・56,000 試行（M-b を m=16 へ）」に書き分ける**（§2-D）。

9. 撤退条件の発火確率表を機械計算で置き、閾値を V′ 実測 0.020 からの両側のずれで定め直すか、観測済みのずれで発火しないことを開示する。天井側（S1/S4/SK）にも撤退条件を置く（§2-I）。
10. 規模行の費用・時間を V′ の**実績**（78,400 試行 ≈ 16.3 時間・約 1.4 ドル）に差し替えて登録者裁定に上げる（§2-J）。
11. `response_mode_M.py` の三点（読むテキスト・「先頭」・復唱除去）を明文で固定する（§2-K）。

13. 門の降格見込みを先置し、「4 中 3」の一般化が到達不能になりうることを読み条項に書く（§2-M）。
