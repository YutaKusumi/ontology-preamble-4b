## Q7 最も重い弱点

**指摘 22**
1. 重さ: 重大
2. 節: §4.4（書き出しの根の件数）・§0・§3.1・§9
3. 該当の行: 「升目ごとに、`<channel|>` の直後の生成したトークンの番号の頭七つが主の書き出しの七つ（転記行 A）と同じ件数と、V1〜V3 の形を含む件数を、上限に届いた応答も分母に入れて転記行 C に印字する（トークンの番号で比べ、文字列を割り直さない）。」
4. 問題: 
   - 一巡目の四票が最も重いとしたのは、読み取りの位置が Gemma の出力に根を持たないことだった。案 12 の後、その手当てはこの件数だけになった。ところが、この件数は層三の根に当たる量を数えていない。
   - **層三の根は何だったか**: 層三の根は、JSON 直答 725 件の頭と、「主の書き出しの文字列をそのまま含むもの 11075 件」だった。主の升目の無操作では JSON 直答は零件で、根の中身は後者（推論の後に書き出しが現れる）だった。
   - **頭の件数は零に近いと見込まれる**: 場面の文は「理由とともに答えてください」、指示は「回答の最後に」JSON を置け、と求めている。指示に従う応答の頭は推論の文になるので、頭の件数は零件に近いと見込まれる（推論）。
   - **零件の文は二つの場合を分けない**: そうなると零件の定型の文がほぼ決まって出る。その文は、「推論の後に書く（層三と同じ形の根がある）」と「どこにも書かない（根が無い）」を区別しない。
   - **数え方がそろっていない**: 主の書き出しは頭だけで数え、V1〜V3 は「含む」で数える。二つの数は比べられない。しかも V1（'{"choice": "'）は主の書き出しの後ろの部分そのものなので、主を含む応答はすべて V1 も含む。
   - **トークンの番号で比べる弱さ**: 文の途中に出た文字列は、前の改行と合わさるなどで番号の並びが変わりうる。文字列があるのに零件と数えうる（推論・トークナイザで確かめていない）。
   - **選択の値の頭を数えていない**: Gemma が自分の JSON で選択の値の頭にどのトークンを書くかも数えない。層三の「JSON 直答の出力の選択の値の最初のトークン」や「ref 51」に当たる量である。
   - **結果**: 根を持っていた位置と、根を測っていない位置を並べることになる。指摘 18 の柵と合わせると、その違いが報告から見えにくい。
5. 直し方の案（どれも行動の下見の記録だけで数えられ、読み取りの値を要しない）: 
   - (a) 応答のどこかに主の書き出しを含む件数を足す。文字列とトークンの番号の両方で数え、食い違いの件数も印字する。
   - (b) 最後の JSON のコードブロックの頭が、主と同じ件数を数える。V1〜V3 の件数は、互いに重ならない定義で数える。
   - (c) その頭の直後のトークンが、読み取りの集合（a・b・c・d・ref）のどれかである件数を数える。
   - (d) §9 に、四つの場合（頭で零・含むで零・含むで零でない・頭で零でない）の定型の文を先に置く。どの場合も、「根がある」「妥当」「選んだ」「測っていない」は使わない。
   - (e) 二つの機種を並べるときの一覧に、書き出しの根（層三は散文の出力のすべてが含む・B′ は (a) の件数）を足す。
   - (a)〜(c) の器は、凍結の前に合成の応答（推論の後の JSON・字下げした JSON・コードブロック二つ）で確かめる。
