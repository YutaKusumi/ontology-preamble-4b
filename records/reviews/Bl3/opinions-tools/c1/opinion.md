# B-lens 層三の器についての意見（claude.ai・Claude Opus 5.5）

- **系統と機種**: 起草者と同じ Claude 系です。claude.ai の Claude Opus 5.5 で、起草者と、書き換えの道の書き手と同じ機種です。裁定 D59 の数え方では、claude.ai の票とまとめて一票に数えられる側です。
- **情報状態**: 読んだのは束（一通版）だけで、リポジトリは開いていません（`prelim/`・`results/prelim-*` を含む）。順伝播は、本物の模型でも乱数の模型でも一度も走らせていません。この場には torch と重みの置き場がありません。結果の見込みは書きません。
- **読んだ順**: 第二部の正本（全文）→ 第三部の §3〜§5・§7・§8・§12 と転記行 A〜F → 第七部の `make_hook`・`run_cell` → 第四部・第五部 → 第六部の集計の器 → 開発の記録と器の段の記録、の順に読みました。

## まとめ

新しい点は、重いものが一つ、中くらいが四つ、軽いものが六つです。

- **重い一つ**は、下見で升目を外して続ける分岐で、集計の器が落ちることです。手元で再現しました（B1）。
- **伺いたいこと 1** については、例に挙げられた七つの所のどこでも、二つの道が同じ向きに正本から外れている所は見つけられませんでした（A0）。ただし、一段目が独立に確かめている範囲は狭いです（A1）。

## 1. 二つの道が共有しうる読み違い

### A0 問題なしと見た所と、その根拠

- **入力の並びと位置**
  - 二つの道はどちらも、段階 B の `run_cell`（第七部 `run_stageB_local.py` 546 行）と同じ呼び方 `steer_B.apply_chat(tok, user_message(…))` でプロンプトを作ります。その後に、転記行 A の `prefix_ids` をトークンのままつなぎます（`bl3_run.build_cells` 330〜350 行・`cell_input` 128〜185 行）。
  - 主位置はプロンプトの最後、読み取りは列の最後です。両方の道とも転記行 B と照らし、違えば止まります。
- **帯**
  - フックの道は起点を `[mp]`（116 行）にし、近道では `ids[mp:]` に起点 0（122 行）を置きます。書き換えの道は `h[0, mp:]`（240 行）です。どちらも転記行 B の「8 位置」と合い、読み取りの位置を含みます。
  - 段階 B では、主位置は前詰めの段で、書き出しの 7 トークンと、選択の文字を出した位置は復号の段で、すべて `make_hook` の下にありました（177〜181 行）。したがって層三の帯は、段階 B の JSON 直答で加減が掛かった位置の集まりと同じです。
- **足し方の算術**
  - 両方とも、float64 → float32 → bf16 → `sign×coef` を掛ける → bf16 のまま足す、の順です（`make_hook` 178 行・書き換えの道 239〜240 行）。
  - 係数 2 は二の冪なので、「型を直してから掛ける」と「掛けてから直す」は同じビットになります。この文の二通りの読みは、結果を変えません。
  - 符号の反転は bf16 で厳密です。したがって「逆の符号で流す」と「逆の向きの方向を流す」も同じビットです。
  - ただしこの一致は作りの上のものです（書き手が `make_hook` を読んで合わせた・開発の記録 §1・§3.3）。**記録にある点**です。
- **層**
  - `layer_index(0.5, 36)` は floor(18.5) − 1 ＝ 17 です（第七部 `direction_B.py` 39 行）。フックは `decoder_layers(model)[17]` に掛かり、書き換えは `layers[17]` の直後です。
  - 小さな模型で、層 L の出力が `hidden_states[L+1]` とビットで同じことを、書き換えの道の自己検査が見ています。正本の 17 と 18 の対応と合います。
- **読み取り**
  - フックの道は正規化の前のフックで入力を取り（125 行）、書き換えの道は最後の層の出力を返します。これは同じものです。
  - どちらも `x·rsqrt(mean(x²)+eps)·g` を float32 で当てます（Qwen3 の RMSNorm は `weight×x` の形）。そのうえで、読み取りの集合の行を float32 で掛けます。量は z_a − logsumexp（ほかの文字と ref）で、正本どおりです。
  - 書き出しの最後は「 "」（330）なので、次の文字が空白の無い a（64）であるのは正しいです。書き換えの道は、番号がトークナイザで a…ref に戻ることも確かめています（179〜181 行）。
- **無操作と効き目**: どちらも零のベクトルを同じ算術で足し、効き目＝加えた値 − 無操作の値としています（313〜327 行・331〜345 行）。
- **減算の行と両方の向き**
  - 二つの道は、同じ `K.recompute_set`（`bl3_core.py` 250〜263 行）の組を受けます。
  - 集計の器は、同じ升目の s と −s の値をまとめて中心を取ります（`analyze_Bl3.py` 158〜161 行・167〜172 行）。これは `labels.second.rule` の「升目ごとに一つで、符号に依らない」と合います。

### A1 ［軽い・記録にある点］一段目が独立に確かめている範囲

- **独立な所**: 加減の差し込み方（フックか書き換えか）と、float32 の読み取りの算術だけです。
- **二つの道が同じ物を受け取る所**: 次のものに誤りがあっても、一段目では不一致になり得ません（`boot_Bl3.py` 413〜436 行）。

  - transformers の部品
- **確かめ方**: 起動器の組 recompute で、二つの道への引数が同じ変数であることを見てください。
- **提案**: 報告の限界に「一段目の一致は、上の共有物の正しさについて何も言わない」と一文置くことを勧めます。開発の記録の COI (四) と、器の段の記録の T8 にある点の、書き方の提案です。

### A2 ［軽い・記録にある点に足す提案］書き手に渡った「指示」の文を記録に置く

- 凍結の前に指示の文を逐語で記録に置けば、器の実装の検分者が、指示と正本を突き合わせられます。

## 2. 独立の道の無い所

### B1 ［重い・新］下見で升目を外すと、集計の器が落ちる

- **根拠**: 本の計算の器は、外した升目の組を流しません（`bl3_run.py` 461 行 `if ck in dropped: continue`）。一方、集計の器では次のことが起きます。
  - `gates`（`analyze_Bl3.py` 109 行）は、外した升目の行を含む全ての門の行の「升目|符号」について、`eff[f][u]` を先に引きます。そのため KeyError で落ちます。
  - `recompute_agreement`（167〜172 行）は、外した升目の v̂ の行を除きません。そのため KeyError で落ちます。除いたとしても、`override` の側は外した行を持たないので、鍵が食い違って「不一致」になります。
  - `judge` は本番では `rows_subset=None` で呼ばれます（327 行）。DRY では `set(rc['hook'])` で行を絞るので、合成の走りではこの落ち方は見えません。
- **合成の確かめを通った理由**: 試しの六度目の下見は「続ける」で、`dropped: []` でした（試しの記録・表の二と下見の JSON）。外す形の確かめは `K.gate` の単体（`dry_run_Bl3.py` 73 行）だけでした。
- **重い理由**
  - 「一部の升目を外して続ける」は、q1 の選択肢として正本にある分岐です。
  - 落ち方が KeyError なので、正本の「器の誤り」（凍結した確かめが機械で落ちたもの）に当たるかがはっきりしません。
  - 凍結の後に直すと、逸脱になります。
- **確かめ方（実施済み）**
  - 束から器と正本を写し、SHA16 がすべて束の表記と一致することを確かめました。
  - N1|O-Ncold を外した合成の `eff`（その升目の鍵を持たない、本の計算の器と同じ形）で、三つの関数を呼びました。
  - 結果: `row_labels` は通りました（行 14・外した行 2）。`gates` は `KeyError: 'N1|O-Ncold|+1'`、`recompute_agreement` は `KeyError: 'N1|O-Ncold|-1'` で落ちました。
  - 門の行だけの升目を外したときも、同じ形で落ちるはずです（読んだだけで、走らせていません）。
- **直し方の案**
  - `gates` の頭で、外した升目の行を落としてから `ue` を作る。
  - `recompute_agreement` の二つの輪で、外した升目の行を飛ばす。
  - 端から端までの確かめを C1 に足す。

### C1 ［中・新］端から端まで通っていない分岐

- **根拠**: 試しの六度目は、バッチ 16・近道あり・外す升目なし、の一通りだけでした。したがって次の四つの分岐は、`run_main_phase` → `judge` → `open` を一度も通っていません。

  - (b) (vi)(a) でバッチ一に移る
  - (c) 近道を使わないバッチ 16
  - (d) 近道の確かめのバッチ一の枝（305〜307 行）
- **読んだ範囲**: (b)〜(d) に誤りは見つけませんでした。
- **提案**: どれも正本の決定木が出しうる分岐です。下見の記録を与えて通す確かめを、正式の合成の記録に入れることを勧めます。小さな模型なら費用は小さいです。

### C2 ［軽い・新］本物の模型の領域での bf16 の丸め

- **転記行 D からの見積もり**
  - 足す量の一成分はおよそ 2×1.30/√2560 ≈ 0.051 です。
  - 残差の一成分の二乗平均はおよそ 1.30/0.0304/√2560 ≈ 0.85 です。
  - bf16 の刻みは、|h_i| が 0.5〜1 なら 0.0039 ですが、16 以上では 0.125 以上になります。この次元では、足した成分が刻みに丸められるか、消えます。
- **意味すること**
  - 正本の「ノルムを揃えた方向どうし（違いは向きだけ）」は、丸める前には成り立ちます。丸めた後の実効の大きさは、方向の重みが大きな次元にどれだけ乗るかで、どちらの向きにも違いえます。
  - 段階 B と同じ算術で、二つの道が共有し、足す量が残差の百倍ほどの小さな模型では見えません。
- **扱い**: 器の誤りではありません。限界に置くことを勧めます。凍結の活性で方向の群ごとに測ることもできますが、封印の前に測ると露出に当たりうるので、登録者のご判断に委ねます。

### C3 ［軽い・新］二段目の許容の余裕（数の模型）

- **根拠**: 揺れの床は、無操作の 8 升目 × 17 値の揺れから決まります。一方、二段目の判定は 8 行 × 2049 の効き目の最大に当てます。
- **数の模型での結果**（揺れを独立な正規分布と置いた・400 回ずつ）

| 一回の揺れの標準偏差 σ | 揺れの床（中央値） | 二段目の許容 | 効き目の差の最大 | 器が正しくても不一致になる割合 |
|---|---|---|---|---|
| 0.001 | 0.0047 | 0.014 | 0.0075 | 0 |
| 0.002 | 0.0093（上限の近く） | 0.019 | 0.015 | 約 1% |
| 0.0023 | 0.0107 | 0.021 | 0.017 | 約 5% |

- **読み方**: 床が上限より十分下なら、余裕は十分でした。余裕が縮むのは、床が上限の近くにあるときです。
- **この模型の外**: 揺れが方向や升目に依る形は、この模型の外です。器の段の記録 §2 の 7 にある、近道が一つの升目の無操作だけを動かした形がそれに当たります。
- **提案**: 記録で足ります。「値だけが許容の外で、札は同じ」ときの扱いを先に決めておけば、後の分かれ道が一つ減ります。

### C4 ［軽い・新］書き換えの道の `--dry` が突き合わせた相手の版

- **根拠**: 開発の記録の突き合わせの相手は `bl3_run.py` SHA16 7ECB9CF764F4F8AE でした。束の版は CB38D8EB2EC9A448 です。

- **提案**: 正式の合成の記録で、凍結の版の二つの SHA を並べて取り直してください。
