## 3. 所見

### 重大

**重大-1 封印した予想の SHA-256 を、採点の時に誰も照らさない**
- (a) 何が
  - 報告の組み立ての器は、封印の記録にある置き場から二つの予想を読んで採点します。しかし、記録に置いた SHA-256 と今のファイルを照らしません。
  - 封印の記録の `freeze_record_sha16` は、どの器も読みません。
  - 起動器の相 pilot・main と本の凍結は、封印の記録が「ある」ことしか見ません。
- (b) どの行で
  - `build_report_Bl3.py:310-311` で予想を読むだけで、:328 は封印の記録の SHA16 を印字するだけです。
  - `seal_Bl3.py:136,144` が SHA を書きますが、読み手はいません（grep で確認）。
  - `boot_Bl3.py:168-170`、`freeze_Bl3.py:292,308-309,315-316` も、封印の SHA を本の凍結に写しません。
  - B-lens では照らしていました：`blens_lens.py:317-327`（`require_sealed`）と `build_report_Blens.py:249`。
- (c) なぜ問題か（壊れる筋書き）
  - 一時の置き場の写しで試しました。封印の後に、コーディネータの q4.gate を「通る」から「通らない」に書き換えました（SHA は 61AA6481… から 4DFF2A4D… に変わります）。
  - `load_inputs` は止まらず、報告の表は書き換えた値を「通らない（一致）」と採点しました。
  - 予想を結果から守る要の柵が、コーディネータ自身が報告を組む所で黙って抜けています。チャットの SHA と git の履歴という外の錨は残ります。
- (d) 直し方
  - `load_inputs` の頭に `require_sealed` と同じ型の確かめを置きます。両方の予想の SHA-256 が封印の記録と同じであること、封印の記録の SHA16 が凍結の記録に写した値と同じであることを見ます。
  - 本の凍結で、封印の記録の SHA16 と二つの予想の SHA-256 を `main_freeze` に写します。
  - 起動器の相 pilot と本の凍結では、二つの予想の JSON がそのコミットにあり、SHA が合うことを確かめます。
  - 「書き換えた予想で止まる」自己検査を足します。

**重大-2 結果を開く段は、一致だけを見る段が見た出力を開いているかを確かめない**
- (a) 何が
  - judge の記録には、読んだ出力の同定がありません。持っているのは parts・tool_error・env・dry・first・second・agree・reason・written_utc だけです。
  - open は judge の記録の `agree` だけを見て、別に与えられた置き場を読みます。
  - open が自分で出し直した二段の一致は、不一致でも止まりません。
- (b) どの行で：`analyze_Bl3.py:401,409`（二つの段が別々に dirs を受ける）・:415-429・:430-432・:359-383。
- (c) なぜ問題か（壊れる筋書き）
  - 合成の組の出力と起動器の DRY の出力の両方で、CLI を通して試しました。
  - judge の後に、Nk の効き目に +1000 を足した写しを、元の judge の記録で open しました。止まらずに開き、`cross:S1:O-Ncold+vNk…` の効き目が変わり、二つ目の札は False から True になりました。
  - Nk の行は再計算の外なので、開いた記録の再計算の一致は True のままでした。
  - v̂ の行を変えた写しでは、open の再計算の一致が False になりましたが、それでも記録を書きました。
  - 組を別のランタイムに分けると、置き場は複数になります（正本は落ちた組の走らせ直しを許しています）。どれを judge し、どれを開いたかは記録に残らず、後から確かめられません。裁定 D219 の門が、同じ出力に結びついていません。
- (d) 直し方
  - judge は、読んだ組の JSON と session の SHA-256、それに凍結の記録と封印の記録の SHA16 を記録に置きます。
  - open はそれと照らし、違えば止めます。open の再計算の一致が judge と違うときも止めます。
  - 起動器の session に、組ごとの JSON の SHA-256 を書きます。
