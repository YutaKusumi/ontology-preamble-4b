### 【新規所見 1（中）】起動器が session.json に記録した `part_sha256` を、集計器（analyze_Bl3.py）が一切照合していない

- **重さ**: 中くらい
- **根拠**: 
  - 第七部 `tools/analyze_Bl3.py:328-344`（`load_outputs` 関数）
  - 第六部 `tools/colab/boot_Bl3.py:510`
  - 第二部 `records/reviews/Bl3/impl/adoption-table-impl-Bl3.md`（R2-重大2 の直し方「起動器の session に組ごとの JSON の SHA-256 を書く」）
- **事象（何が起きているか）**:
  `boot_Bl3.py:510` において、各組（part）の計算完了時にその JSON の SHA-256 が `SESSION['part_sha256'][part] = sha256f(...)` として `session.json` に記録されるようになりました。
  しかし、これを受け取る側の集計器 `analyze_Bl3.py` の `load_outputs` 関数では、手元で `sha256f(p)` を計算して `files[part]['json_sha256']` に格納しているだけで、**`session.json` の中に書かれている `S.get('part_sha256', {}).get(part)` と手元のファイル `p` の SHA-256 が一致しているかどうかを一切照合していません**（grep でも `part_sha256` は `boot_Bl3.py` と `dry_run_Bl3.py` にしか現れません）。
- **なぜ問題か（壊れる筋書き・止まるべき所で止まらない）**:
  R2-重大2 の対策として、`judge` と `open` の間は `files`（json_sha256, session_sha256）の照合によって強固に結ばれました。しかし、**「Colab 実行終了後から手元で judge を走らせる前までの間」に `main.json` が破損または改ざんされた場合**、`judge` はその改ざんされた `main.json` の SHA-256 をそのまま `inputs` として信じて記録し、`open` も同じ改ざんファイルを開いて通過してしまいます。
  せっかく Colab のランタイムが「自分が生成した組の真の SHA-256」を `session.json` に刻印して zip で持ち出しているのに、集計器がそれを照合しないため、Colab と手元の間の改ざん検知柵が 1枚抜けた状態（何も捕まえない）になっています。
- **確かめ方**:
  手元で `boot_Bl3.py` の相 main を走らせた出力ディレクトリにおいて、`session.json` はそのままにして `main.json` の数値を書き換え、その状態で `python tools/analyze_Bl3.py judge <dir>` を走らせると、`session.json` に残る真の SHA-256 と食い違っているにもかかわらず、`judge` は何のエラーも出さずに改ざん後の SHA-256 を `inputs` に記録して終了します。
- **直し方**:
  `tools/analyze_Bl3.py` の `load_outputs`（行 339 付近）に以下の照合を足します：
  ```python
  if S.get('part_sha256') and part in S['part_sha256']:
      got_sha = sha256f(p)
      want_sha = S['part_sha256'][part]
      if got_sha != want_sha:
          raise SystemExit('組 %s の JSON の SHA-256 が session.json の記録と違う（破損または改ざん）: %s != %s' % (part, got_sha, want_sha))
  ```
  ※なお、`dry_run_Bl3.py` の `e2e` はメモリ上の辞書を渡しているため影響を受けず、`part_boot`（五の相）でも `boot_Bl3.py` が `part_sha256` を正しく書くため正常に通過することを確認できます。
- **扱い**: 凍結の前に直すべきもの（直しは極めて局所的で安全です）。

### 【新規所見 2（軽微）】報告の組み立て器（build_report_Bl3.py）が `judge-Bl3.json`（一致段の記録）の SHA16 を照合していない

- **重さ**: 軽い
- **根拠**:
  - 第七部 `tools/analyze_Bl3.py:478`（`A['judge_record_sha16'] = judge_sha16`）
  - 第七部 `tools/build_report_Bl3.py:339-368`（`load_inputs` 関数）
- **事象**:
  `analyze_Bl3.py` の `open_checked` では、引数として受け取った `judge-Bl3.json` の SHA16 を `A['judge_record_sha16']` として `analysis-Bl3.json` に埋め込んでいます。
  しかし、報告を組む `build_report_Bl3.py` の `load_inputs` は、封印記録（`sealing-record-Bl3.json`）や凍結記録（`FREEZE-RECORD-Bl3.json`）は厳格に照合しているものの、**手元の `records/Bl3/judge-Bl3.json` が存在するか、あるいはその SHA16 が `A['judge_record_sha16']` と一致しているかを照合していません**（また、`tools/sweep_Bl3.py` も `judge_record_sha16` の存在を必要条件に含めていません）。
- **なぜ問題か**:
  `analysis-Bl3.json` は通常 `analyze_Bl3.py open` でしか作られないため実質的な害は小さいですが、正規の手順（judge → open → build）を踏んだ証拠である `judge-Bl3.json` との連鎖が報告生成の入口で途切れています。
- **確かめ方**:

## 3. 伺いたいこと 3: 器の決め（第二部 B表の「変えない」とした決め）

第二部 採否案 B表および第八部 §13 に記載された「変えない」とした器の決め（R1の13項目、R2の11項目のうち非変更分）について精査しました。

主要な項目についての確認理由は以下の通りです：

- **R1-1（バッチ並びの種の鍵は升目・符号の通し番号）**:
  外した升目の組があっても番号を詰めることなく `key_index` を割り振っています。これにより、ある升目が外れても「残った他の升目のバッチ内順序」が不変に保たれます。決定論的再現性の観点から極めて合理的です。
- **R1-2（無操作バッチの先行と揺れの影響）**:
  無操作バッチを先頭に流すことで、後続の層ごと差分計算に必要な `noop_h` を確実に確定させています。無操作の揺れが同一升目・符号内の全効果に同等に乗る特性は、p値や順位（差の順序）には影響を与えず、零との比較や四分位境界にのみ入る仕様であり、正本の設計思想と整合しています。
- **R1-8（裾の本数が等しいときは 'tie'）**:
  裁定 D232 により、独立の再計算で裾の一致を比較するのは「等方の外の行」（Holm通過行）に限定されました。Holm通過行で帰無の両側の裾の本数が一致して tie になる確率は実質的にゼロであるため、この境界処理が二段一致の判定を歪めるリスクはありません。
- **R1-10（書き換え器の既定 use_cache と呼び出し時の use_cache=False）**:
  外部個体が作成した `bl3_recompute_rewrite.py` は改変せず、呼び出し元である `boot_Bl3.py` および `dry_run_Bl3.py` 側で `use_cache=False` を明示的に指定してフック側の計算条件と一致させています。責任分界とコードの保全上、適切な判断です。
- **R2-15（起動器の版照合から scipy を除外）**:
  Colab 環境において、使用していない `scipy` を pip で無理に完全一致させようとすると、CUDA 依存の再解決が走り torch や torchvision が破損するリスクが高くなります。計算本体が scipy を一切 import していないことを確認しました（numpy と torch のみ）。除外理由が docstring に明記され session にも版が記録されているため、実務上極めて健全な判断です。
