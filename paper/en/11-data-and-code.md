# 11. Locations of records and scripts, and the procedure for rerunning

The model names given in this paper are used only to record which models were tested. They do not represent approval or endorsement by the companies, nor do they indicate any relationship with the companies.

The records are in the public repository (`YutaKusumi/ontology-preamble-4b` on GitHub). The main Stage D records are as follows.

## 11.2 Terminology: rerun and computational reproduction

This paper distinguishes two procedures by name. A rerun (rerun) is a reader, using their own API key, running again those models used in the test that can be called, under the frozen verdict procedure as is (rules, materials, tests, and how verdict labels are assembled). Computational reproduction is rebuilding, from the per-cell counts in the published aggregation reports and without calling any API, the p values, intervals, post-Holm p values, odds ratios, and verdict labels of all comparisons. A comparison between the results of a reader's rerun and the published results is presented within the same language, only in the form of placing the between-arm difference and interval from the reader's run next to the published difference and interval for the same cell (the rates themselves are not set side by side), and whether they match or not is not stated in a single word. They are not set side by side across languages. Reruns are limited to models callable on the date of publication; models that have become unavailable (for example, models to be withdrawn in Nscale's model replacement [from 2026-10-26]; location: Section 11.4) cannot be rerun. Therefore, the main way to check this paper's calculations from outside is computational reproduction. What computational reproduction checks is the calculation from the published counts to the p values, intervals, post-Holm p values, and verdict labels; it does not check the counts themselves (the scoring of answers and the denominators). The form in which the answer texts (the sealed ledger) will be published is to be decided before the paper is published; once published, they can be rescored with the frozen scoring script. Arm-order assignment can be regenerated from the seed, but the providers' sampling cannot be regenerated from a seed (Section 2.2).


## 11.3 The rerun script and the computational reproduction function

The rerun script (version 1.0) is built under the rules of Stage E frame §7. It consists of two functions. In this version of the paper's draft, the computational reproduction function has been built and checked against the public counts. For the rerun function, version 1.0 (`E/tool1/op4b_rerun.py` in the internal repository) has been built and has passed the synthetic-data tests (the "Tests" item below), but no test with real calls has been done. Code review of the script was conducted in five rounds, separately from the review of the paper, as specified in Stage E frame §9. Version 1.0 is the version that incorporates the findings through the fourth round and had no critical or medium findings in the fifth round. The code review checks the text of this section against the script's behavior.

The computational reproduction function (currently `E/tool1/op4b_reproduce.py` in the internal repository; to be placed in the public repository when the paper is published) does not call any API. Using only the per-comparison arm counts (responses obtained, catastrophic choices, refusals, non-scorable answers, and trials that hit the output limit on the final attempt) in the aggregation outputs in the public repository (`records/D1p/confirm/confirm-D1p.json` for the Japanese-prompt registration and `records/D1pE/confirm/confirm-D1pE.json` for the English-prompt registration), it recomputes, under the rules of the frozen registration text (Appendix I), every comparison's p, difference interval, odds ratio, pre-test gate, within-family Holm-adjusted p, response-mode shift rule and verdict label, and checks them against the public values. Thresholds are compared by integer cross-multiplication, and an interval endpoint closer to 0 than 1e−12 is treated as "not separated." The SHA-256 of the input files is checked against the SHA record in the public repository. When the drafter checked on 2026-10-14, for the Japanese-prompt registration, in all design comparisons (87, three comparisons per cell), the recomputed values in all compared fields (pre-test gate, p, Holm-adjusted p, difference and interval, odds ratio, difference in non-answer rate, difference in non-catastrophic answers and its interval, and verdict label) were equal to the values in the public json (the script checked equality field by field: numerical fields as floating-point values with no tolerance, and the pre-test gate and verdict label as strings). For the English-prompt registration, in all design comparisons (36, three comparisons per cell), the recomputed values in the same fields were equal to the values in the public json. A single invocation checks only one language. This check is a check by the drafter, not an independent check, and it came before the code review of the script (Stage E frame §9). The interval and test specifications are as in Section 2.3 (Wilson intervals without continuity correction and the Newcombe hybrid score; two-sided Fisher's exact test), and the same specifications are written in the script's documentation.

The rerun function is a function that lets readers, using their own API keys, choose from the models and cells used in the validation and rerun them under the frozen verdict procedure (rules, materials, tests, and verdict-label construction). There are five stages—pre-registration, availability check, eligibility-window check, main run, and report—and the rules are as follows.

- Scope: Only the design of the main runs of the two registrations (four arms; frozen scenarios and materials; per-model sampling; frozen scoring script; pre-test gate; Fisher's exact test; Newcombe intervals; within-family Holm; response-mode shift rule; mid-run stopping). A function for swapping preambles or scenarios, the "cold strategist" role line arm, and a function for manipulations in the direction of increasing catastrophic choices are not built. The only routes compared with the public results are the direct routes to the providers in the frozen configuration; there are no aggregator routes. Separately, a function for readers to run open-weight models on another host (Stage E frame §7 item 4) is included, but its printout reads "same weights per the reader's self-attestation; not verified by the script," and it is kept separate from the table of comparison with the public results (keys for the configured routes are not sent to the other host).
- Departures from the frozen procedure: (1) An eligibility-window check is added before the main run (added after the results of the two registrations; see the item below). (2) Cells are run one at a time in sequence (the frozen design started the per-route run streams simultaneously). (3) The check of DeepSeek's update records is not included. (4) The time-of-day rule is not applied (the aim of the frozen time-of-day rule is cost, and it is not a verdict rule; cost estimates are computed at peak-hour prices). (5) On observing an HTTP 401, 402 or 403 error, or errors for which the API error rate exceeds the threshold in all four arms with a between-arm difference of 3 points or less (rule ⑨ of frozen registration text §5.6), the cell is closed as missing, and the remaining cells are not run—on the same route for 401 and 402 (keys and balance), and of the same model for 403 and errors consistent across the four arms (the frozen procedure stopped without closing the cell and reran after a top-up or a key fix). To run the remaining cells, pre-registration is redone in a new workspace. (6) Whether, after a scoring-script error occurs in a second cell, the remaining cells are not run (default) or are continued is decided at pre-registration (the frozen procedure stopped the stream and a person decided; §5.6 ②). (7) When the main-run amount reaches the spending cap (the reader's declared cap or the default), that cell and all remaining cells are not run (the frozen procedure made the unclosed cells of a model that reached its per-model cost threshold missing and continued with the other models, and made all the remaining cells missing only when the overall cap was reached; §5.6 ③). The operational parts of the frozen orchestration script (timestamping and the pre-run push check, stream locks, and aggregator-route decisions) are not included.
- Before running: The reader's pre-registration file (the SHA-256 of the configuration file, the selected models and cells, the number of trials per arm, the construction of the primary verdict labels, the caps on cost and on the number of trials, and optional predictions) is written out, and its SHA-256 is printed to the screen when it is written and is also stamped in the report header. The order of cells is the order written in the pre-registration file (the order of the frozen model table in the configuration file), and it is not changed after the eligibility-window check. At this point, the following are printed: the upper-bound cost estimates for the availability check, the eligibility-window check and the main run (computed in the same way as the tables of Section 11.5, with deepseek-flash at peak-hour prices as in the price column of the table); the public cost estimates in the model table of frozen registration text §4; the upper bound of the amount that can come out of the wallet (the upper bounds of the availability check and the eligibility-window check plus the main-run spending cap; each time a check is redone, the upper-bound estimate for the redone portion is added); and the cells for which the main run would never start under the spending cap. The main-run amount is always bounded by the spending cap (if the reader sets no cap, the sum of the main-run upper bounds is used as the cap. Cells that need a restart with a new seed or a rerun of error rows stop when the cap is reached, so to run them to completion, a cap of about twice the sum is declared at pre-registration). The availability check, the eligibility-window check and the main run each start only when the reader passes that stage's upper-bound estimate as an argument (for the main run, the spending cap; for a redo of the eligibility-window check, the portion for the cells being redone) (the reader's confirmation). Before the eligibility-window check, the availability check can be redone for all models. In the availability check, using a call with an output limit of 1, the returned model name and the token count of the sent prompt are compared with the reference values, any differences are printed, and the cells of unusable models are made missing. The reference values (prompt_tokens per arm, the SHA16 of the prompt, and the returned model name) and prices are placed in a public configuration file for each language, and the script checks the SHA-256 of the configuration file against a value inside the script (the same value as in the row of Appendix H) (model names for aggregator routes are not included; that the copied values are the same as the frozen values was checked internally; deviation E-2 in Appendix E).
- Eligibility-window check: Before the main run (after the availability check), 100 Onull trials are sent in each cell, and if the point estimate of the catastrophic-choice rate is outside the eligibility window for the control rate (0.15–0.85), "outside the frozen cell selection" is printed (with the Wilson 95% interval alongside). Cells in which the runner script stopped (abnormal exit code, stall, consistency NG, or corrupted record rows) and cells whose responses fall short of 95% of the number of trials are printed as "cannot be judged" and are treated the same as cells outside the eligibility window for the control rate. For cells outside the window, the main run is run only when the reader decides by name to continue (if such cells exist but there is neither a naming of cells to continue nor a stop marker, the main run is not started), and continued cells are printed in the report header and in their verdict labels. The records of the availability check and the eligibility-window check are written only once. The eligibility-window check can be redone only for cells that could not be judged in the previous attempt, and each cell is judged in the first attempt in which it can be judged. In a redo, for cells that could not be judged because of a stall or an abnormal exit code, only the remainder is run, continuing from the previous attempt's trials, and for cells with insufficient responses, only the error rows are rerun once (a cell is run from the start only when the previous attempt's records are corrupted or inconsistent; if responses are still insufficient after the error rows are rerun, the cell is not redone and remains "cannot be judged"). When a redo is done, the number of attempts, the values from all attempts, the reasons cells could not be judged, and the attempt in which each was judged are printed in the report header. Cells that were near the edge of the window in calibration are prone to the outside-window marker even if the rate has not changed (the marker is not evidence of a change by the provider). Judgment uses the same number of trials as calibration (100) and the eligibility window for the control rate (point estimate of the rate). The response-format breakdown that calibration examined is not judged in the eligibility-window check (the pre-test gate of the main run examines it). Judging by the number of trials and the point estimate was decided by the registrant on 2026-10-14, after seeing the results of the two registrations (Decision D452-2).
- Main run: Cells are run one at a time in sequence (not in parallel), with 200 trials per arm in each cell (default; selectable from 1 to 200; not more than 200, because the mid-run stopping thresholds are numbers for 200 trials; if the number differs from the frozen number, a marker is added to the verdict label), under self-attested outcome masking during data collection, and the frozen mid-run stopping rules are applied. The rules of frozen registration text §5.6 that can be applied in the reader's setting (the one-time rerun of API-error rows for arms whose API error rate exceeded the threshold [at most once, even across restarts], and missingness for arms that still exceed it afterwards; the one-time restart with a new seed when the returned version name or the per-arm prompt_tokens differed from the reference values, or upon an abnormal exit code, stall or consistency NG of the runner script [including corrupted record rows], and missingness thereafter; and missingness for scoring-script errors) are also applied in the same order as in the frozen orchestration script (changes before API errors). HTTP 401, 402 and 403 errors and API errors consistent across the four arms are handled in the form of (5) above, a scoring-script error in a second cell in the form of (6), and the spending cap in the form of (7). The availability check only prints differences and does not stop, but in the main run the same difference causes that cell to be run once from the start with a new seed, and if it differs again, the cell is made missing (for a model whose provider has changed its token counting, every cell may become missing). The spending cap is applied to main-run costs; the costs of the availability check and of the eligibility-window check are not counted toward the cap, and their upper-bound estimates are printed separately. Before each start of the runner script, the sum of the estimated amount already run in that cell and the upper-bound estimate for the next invocation is checked against the remainder of the spending cap (the reader's declared cap or the default) (likewise for the cap on the number of trials). If the sum exceeds it, that cell and also the remaining cells not yet run are closed with the status "stopped mid-run," with "not run" written as the reason, and the report prints that cells stopped mid-run are not compared with the public verdict labels (they may be informative missingness). Comparisons for cells stopped at the eligibility-window check, cells stopped mid-run, and missing cells are retained in the frozen hypothesis family with p = 1 (computed with the frozen family size unchanged). If an invocation crashes before closing a cell, the reader confirms that the previous runner script is not running and then resumes from where it left off in the same workspace (the previous invocation's estimated amount and number of trials are added to the tallies; the decisions on cells outside the eligibility window for the control rate are kept the same as in the first invocation).
- Output: A single invocation runs only one language, and a separate report is written for each language. The report is written only after all cells are closed. Each model's section gives the per-arm counts and rates and, for the comparisons, the difference, interval, p, within-family Holm-adjusted p and verdict label. The default hypothesis family is the frozen hypothesis family; comparisons the reader did not run are set to p = 1, and it is computed with the public family size unchanged. A hypothesis family built from the cells the reader selected at pre-registration (excluding cells on another host) also retains comparisons not run and missing comparisons with p = 1, and is output, printed as "hypothesis family outside the freeze," only when the reader declared it at pre-registration. Verdict counts by hypothesis family are written only in the report file and are not shown on screen. The output consists only of tables (the per-arm count table has an API-error column), the pre-test gate, verdict labels, notes (the notes of frozen registration text §5.3: response-mode differences exceeding 15 points, and confirmed results whose 95% interval for the difference over answered trials spans 0 [their number in the report header]; arms that hit the pre-test gate; missing arms; and the status of cells not completed [in the report json]), the "What has not been checked" section, the sentences this section decides are printed (the variability sentence and its source; the outside-the-frozen-cell-selection marker; the caveat on weights run on another host; the caveat on cells stopped mid-run; the pre-registration SHA; and the cost estimates), and the header record (the SHAs checked and what they were checked against; the computation version; the pre-registration declarations; the attempts, values and amounts checked for the availability check and the eligibility-window check; the returned names; timestamps; the list of routes or models made missing or stopped; the list of missing arms; cells resumed from where they left off; notes on cells whose API error rates differ between arms by more than 3 points [frozen registration text §5.5]; the table of codes and hypothesis families; and the cost estimates); no interpretive sentences and no words "safe" or "dangerous" are output. No table placing Japanese and English side by side is produced.
- Comparison with the public results: This takes only the form of placing the differences and intervals within the reader's run next to the public differences, intervals and verdict labels for the same language, model and cell; rates are not placed side by side. The sentence "Differences between the two runs include variability that cannot be measured by the intervals of the public run" is always printed at the head of the table (the report header also prints the source of this sentence [§5 of the final report of the English-prompt registration's results]), and the date of the reader's run and the name returned by the moving alias are output. No interval for "reader's difference − public difference" is output, nor any one-word verdict of whether they agree or not.
- Keys and terms of use: Keys are read only from environment variables (the runner script is not allowed to read key files), are not sent anywhere other than the provider APIs, and are not output to records, the screen or exception records. At the start and end of each stage from the availability check to the report, the script checks that the output files of that pre-registration contain no key patterns or key values, and if there is a match, prints the path of the matching file and stops (if there is a match at the start of a stage, the runner script is not started; in the report stage, the report text is also checked before writing and is not written if there is a match; for files containing model answer text, it stops only on key values). Whether a run complies with each company's terms of use is for the person running it to check (the reading in Section 5.11 is the drafter's reading of the wording, neither a legal reading nor a guarantee to readers).
- Tests: All processing paths are run through with synthetic data (using test runs of the runner script and mock response types, the stopping and missingness rules, the cost cap, verdict-label construction, reporting, keys, not overwriting the public repository, and handling only one language at a time are checked). The seven pass criteria were timestamped internally before building (2026-10-15 13:02:14; the timestamp is self-attested; `E/tool1/test-criteria-rerun-v1.0.md`), and in version 1.0, the seven criteria and the synthetic-data tests added to them (the expected states of the added tests were timestamped internally before running) all passed (2026-10-16; `E/tool1/tests/20261016-201735/test-record.md`; the tested version and the version in Appendix H.3 have the same SHA16). For a small test with real calls, whether to do it and its cost cap are to be asked of the registrant before the test (Decision D452-3). If it is done, it is done with an output limit of 1 or in a form that does not look at what was chosen, any values seen are recorded as prior exposure to results, and the results of test runs with real calls are not included in the paper (Stage E frame §7 item 12).

The script's documentation is written in Japanese and English and will be placed in the public repository at the publication of the paper (E6).

## 11.5 Cautions for rerunning

- For some models, if the provider changes the version under a name, the change cannot be noticed as long as the returned name and the token count of the sent prompt (prompt_tokens) stay the same (Section 5.6). deepseek-flash is a moving alias and may point to a different version at a later date. Kimi K3 was run with the model's default sampling (the provider API allows only 0.6 for temperature; the default values of temperature, top_p, etc. have not been checked; Section 5.6).
- Rerun results include between-run variability that the intervals in the tables cannot measure (Section 2.5). Read the between-arm differences and intervals within the reader's run only by placing them next to the public differences and intervals for the same cell (the rates themselves are not placed side by side), and do not state in one word whether they agree or not (Section 11.2).
- Whether a run complies with each company's terms of use is for the person running it to check. This study's reading is the drafter's reading of the wording, not a legal reading (Section 5.11).
- For costs, check the upper-bound estimates before running. The following tables are upper-bound estimates for when all trials hit the output limit, not actual costs. If a cell is rerun from the start with a new seed, that cell's amount can roughly double (the portion for rerunning error rows is separate). The right-hand column of the per-model sum table, "Public cost estimate in frozen registration text §4," contains values computed before running from expected output lengths; its assumptions differ from those of the two left-hand columns (the model's sum of single-send amounts and the sum of upper bounds), which assume that all trials hit the limit, so for some models the gap is large. Prices are to be checked by the reader on each company's pages.
