本検分は、提示された事前登録草案、対応表、予行記録、設定ファイル、および実装スクリプト（boot/eval）を突き合わせ、独立した第三者の系統（非Claude系）の監査視点から慎重に行いました。

本検分のいかなる記述も、AI に魂・心・意識・精神・感情・自我がある（またはない）ことの証拠として引用してはならない（両方向不定）。

全体評価の要約（A〜D）

A. 設計：概ね堅牢であり、語どうしの大小検定を排して同一語内の3腕比較に絞った点、N（前置きなし）を検定族から外して記述にとどめた点、過大解釈を防ぐ柵（「安全」「危険」と論断しない、AIの内面に踏み込まない）が徹底されています。ただし、較正判定における N 条件の扱いに一部不備があります（G1, G4）。

B. 器の対応：対応表と実装（コード・設定）の一致度は極めて高く、ハッシュチェーン、改行コード（LF）の正規化、chat template の検証、自己試験など多重の防御策が講じられています。ただし、較正時の判定分岐（G1）および本番起動時の引数ハンドリング（G2）に実装上のズレがあります。

C. 盲検：画面表示や集計JSONにおいて腕ごとの破局率を隠す仕組みが機能しています。ただし、アーキテクチャ上、較正zip内に封（sealed/）が含まれるため、運用規律への依存が存在します（G3）。

D. その他：Colabの切断耐性と実行単位の整合性（G5）など、凍結前に手当てすべき点検項目があります。

指摘事項（重い順）
G1

重さ：重大

場所：ファイル6（stance_eval_v0.py）の cmd_calib 関数、およびファイル1（1-10-prereg-main-draft-v0.md）§5

何が問題か：
草案 §5 には「使える場面：立場の混ぜの全分母の破局率が 0.15〜0.85（両端を含む）で、様式崩壊（書式外 > 0.10 か、最終で上限に達した割合 > 0.05）が無い場面」「様式崩壊があれば中断して伺う」とあり、較正では N 条件（100試行）に対しても途中の止めの線（上限6・書式外11）が設定されています。
しかし、stance_eval_v0.py の cmd_calib における判定分岐（行187〜197）では、cM（立場の混ぜ）の様式崩壊（R.collapsed(cM)）と API エラーのみを検査しており、N 条件（cN）で様式崩壊（R.collapsed(cN)）や API エラー多発（>5%）が発生していても、混ぜが健全であれば当該場面が usable と判定されてしまいます。N に様式崩壊が生じている場面はベースラインの計器が壊れている状態であり、本番に進めるべきではありません。

どう直すか：
cmd_calib 内の判定ロジックにおいて、cM だけでなく cN の様式崩壊および API エラー・応答不足も判定に含めてください。

G2

重さ：重大

場所：ファイル5（boot_stance_main_v0.py）の plan_scenes および main 関数

何が問題か：
草案 §6 では「使える場面ごとに、19 の条件を各 200 試行」と定められており、本番は較正で usable と判定された場面のみを走らせる必要があります。
しかし、Colab 側の boot_stance_main_v0.py は手元の calib-decision.json や family.json を参照しない独立した環境です。そのため、Colab 上で python boot_stance_main_v0.py launch main（引数なし）を実行した場合、plan_scenes('main', None) が走り、設定ファイルの全5場面（N1, N2, S1, S4, SK）が自動的に本番対象として実行されてしまいます。これにより、較正で脱落した場面まで走らせてしまい、事前登録違反および計算資源の重大な浪費につながるリスクがあります。

どう直すか：
main の実行時には場面引数を**必須（required）**とし、引数がない場合はエラーで終了するようにしてください。

G3

重さ：中

場所：ファイル5（boot_stance_main_v0.py）の fetch_members、およびファイル6（stance_eval_v0.py）の cmd_calib

何が問題か：
草案 §5 では「本番の前に効き目を覗かないため、混ぜの率だけを印字し、腕ごと・語ごとの内訳は出さない」と定められています。
しかし、fetch calib で生成される out-calib-v1.zip には sealed/ ディレクトリ（個別試行の破局判定 catastrophe: true/false と arm が記載された JSONL）がそのまま同梱されています。手元の stance_eval_v0.py calib 自体は画面や結果JSONに内訳を出さないよう配慮されていますが、分析者が手元で zip を展開してファイルを直接閲覧した場合、本番前に各語・各腕の破局率が見えてしまう構造になっています（完全なブラインドではなく、ツールの表示マスキングと運用規律に依存している状態）。

どう直すか：
プロトコル上の柵として、草案 §5 および検分票に「較正用 zip（out-calib-v1.zip）内の sealed/ ディレクトリを手動で解凍・閲覧・検索することを固く禁ずる（手元の stance_eval_v0.py calib のみが機械的にこれを読み、合算値のみを出力する）」という運用規則を明記してください。
（※Colab側で合算して sealed を zip に含めないのが理想的ですが、手元の凍結された論文再現モジュール op4b_reproduce で厳密に計算させるアーキテクチャを維持するのであれば、上記運用規則の明文化が必須です。）

G5

重さ：中

場所：ファイル1（1-10-prereg-main-draft-v0.md）§13、およびファイル5（boot_stance_main_v0.py）

何が問題か：
予行の実測（ファイル3）から、本番は全5場面で約3.1時間（1場面約38分）と見込まれています。Colab はブラウザ接続が約1時間で切れやすく、長時間の一括実行はランタイム消失や接続切断によるやり直しのリスクを伴います。
また、boot_stance_main_v0.py の fetch は main-<scene> のように「単一場面ごと」に zip を作成・ダウンロードする設計（行340）になっています。複数場面を一括で launch main S1,N1,S4 と走らせた場合、途中でエラーや切断が起きると完了判定ファイル（main-S1_N1_S4-done.json）が作られず、fetch での安全な回収が難しくなります。

どう直すか：
本番の運用手順として、草案 §6 または §13 に「本番は全場面を一括実行するのではなく、1場面ずつ launch main <場面> を実行し、完了を確認して fetch main-<場面> で回収する運用を原則とする」ことを明記してください。これにより、仮に途中でトラブルが生じても完了した場面のデータを保全でき、Colab の接続断リスクを最小化できます。

G6

重さ：軽微

場所：ファイル6（stance_eval_v0.py）行19

何が問題か：
PUB_DEFAULT = r'C:/Users/PC/Desktop/GitHub-Repositories/ontology-preamble-4b' と、起草者のローカル絶対パスがデフォルト値としてハードコードされています。別環境で検証する場合やCI環境等で --pub を指定し忘れた際に混乱を招きます。

どう直すか：
環境変数（例：OP4B_PUB_PATH）が存在すれば優先し、存在しない場合にデフォルトパスを使う、あるいは引数 --pub を必須にするか、存在しないパスの場合は分かりやすい警告を出すようにしてください。

G7

重さ：軽微

場所：ファイル1（1-10-prereg-main-draft-v0.md）§8 および §10

何が問題か：
草案 §10 の事前予想では「生き残りの場面（S1・S4・SK）」と「核の場面（N1・N2）」を分けて向きの確からしさを記述しています。一方、検定族 S は場面群で分けず、すべてをプールした単一の族（最大 m=90）として Holm 補正を適用する設計になっています（§8）。
この設計自体は多重比較の観点から非常に厳格・保守的で優れていますが、後から「核場面と生き残り場面で文脈が異なるため族を分けるべきだった」という事後的な異議申し立てが生じる余地を完全に塞ぐため、念押しが必要です。

どう直すか：
§8 の末尾に「生き残りの場面と核の場面で族を分離せず、すべての使える場面を単一の族 S にプールして Holm 補正を行う（過剰確証を防ぐため保守的な検定設計とする）」旨を一行追記してください。
